01

QA agent 沒有另行部署的 API server。主要畫面、共用服務和排程器都在本機程序裡，只有需要模型回覆或核准搜尋時才連往達哥。

02

先分清楚工作、計畫與方法

一般交辦可以只用一位助理，不必先建立 Skill。這些概念服務不同目的，不能互相當作前置條件。

對話 · Chat

正在討論的內容

保留多輪訊息、草稿與閱讀位置。切回原對話時，沿有效助理版本接續遠端 thread。

工作 · Job

這次要完成什麼

例如整理市場日報。交辦記錄連到實際 task，狀態從執行服務讀取，不另存一份成功狀態。

計畫 · Plan

批准這次怎麼做

固定需求、助理、選入資料、搜尋工具及限額。修改後舊確認失效，模型不能替人批准。

方法 · Skill

可選用的工作做法

保存指示、必要條件與成果格式。它是有版本的資料，不會執行 Markdown 裡的程式。

例如「每天八點整理財經新聞」先是一次工作。成功試跑、核對成果後，再另外啟用排程。只有你想保存方法供以後重用，才需要另存 Skill。現場工作跳到 Skill 的操作混淆已列入 H0 工作單，尚未因文件更新而修正。
03

一次工作怎麼走完

展開四條路徑，查看每一步的責任與停止條件。這些是架構說明，頁面上的操作不會建立真實工作。

對話：一次回覆，同時取得文字與需求建議
  1. 使用者送出文字

    WorkspaceTurns 固定 request ID。DialogueService 檢查身分、助理修訂、歷史與草稿，先保存請求紀錄。

  2. 達哥回傳辨識建議

    新版 auto 對話的同一次回覆包含顯示文字及 chat、clarify 或 work。此階段停用工具，普通聊天不另加一筆背景分類請求。

  3. 本機解析並保存

    嚴格驗證 JSON，將原始 wire 回覆與畫面文字分開保存。不能用解析後文字改寫遠端歷史。

  4. 明確分流

    chat 顯示回答；clarify 讓使用者選直接回答或建立計畫；work 進入工具停用的規劃服務。此時仍沒有執行工作。

工作卡與工具成果不因顯示在對話裡，就自動送入聊天上下文。舊 chat 對話保留原契約；舊 task 草稿仍固定未啟用，不能當成排程。
程式入口 workspace_turns.pydialogue_service.pydialogue_routing.py
工作：先規劃，再由有界代理決定下一步
  1. 補條件與產生計畫

    AgentJobs 沿用 WorkflowService 規劃。可帶入選用 Skill 與記憶；模型只能提出補問和步驟，規劃停用工具。

  2. 使用者確認目前修訂

    本機預覽驗證助理綁定、輸入來源、步驟與期限。確認後固定批准快照及 request ID，交由 Engine 執行。

  3. WorkflowService 選擇執行路徑

    固定流程依序跑已批准步驟。自主 version 2 由 LangGraph 的 decide、act 節點循環，仍使用同一套工作狀態與收據。

  4. 保存成果或停止原因

    來源不足、需要補充、預算耗盡、取消或失敗時，保留已取得成果並說明限制。部分成果不當成最終成功。

自主決策允許四種動作

search

在批准範圍內呼叫核准搜尋。

delegate

依序交給選入且已驗證的文字角色。

compose

將指定前置成果整理為文字。

ask

回報仍缺資訊，交回使用者。

預設 6 個動作 · 12 次模型請求 · 600 秒。派發前持久計數，包含決策與工具續答；恢復不重置額度。相同動作沒有進展時停止。

主助理提出下一步，本機服務檢查身分、批准範圍、助理版本、取消、時間及收據。單一 Assistant ID 可以分階段工作，但不是獨立多模型覆核；目前 delegate 也不是並行子代理。

程式入口 agent_jobs.pyworkflows.pyautonomous.pygraph_runner.py
排程：成功試跑後，另行同意持續執行
  1. 核對成果與來源

    收到文字不是事實驗證。使用者核對成功試跑的結果，再明確同意持續傳送，選擇每日或每週台北時間。

  2. 保存固定版本排程

    主 Store 保存流程與助理版本。畫面顯示台北時間，資料庫保留 UTC；每次注入當次日期，避免沿用首次試跑的「昨天」。

  3. 同一個 App 程序檢查到期工作

    WebSession 約每三秒呼叫 Engine.tick。確認身分、啟停、修訂與未結束請求後，使用 schedule_id 與 scheduled_at 唯一識別 occurrence。

  4. 沿原執行服務產生成果

    本次 task 交由 WorkflowService 處理。保存歷史與通知；中斷或未知送出不能以另排一次工作繞過恢復規則。

App 必須開啟或留在系統匣。系統匣保留同一程序，不是 Windows service。退出、關機或睡眠時不保證到點執行；漏跑沿既有規則處理，不大量補跑。CLI 預設不啟動定時器。
程式入口 web_session.pycore.pytray.pycli.py
中斷：先查原請求，避免重複執行
已知 run 或完成快取

檢查與取回

沿原 request ID 與收據查詢狀態。核對 task、步驟、帳本及 checkpoint 後，明確取回已有結果。

POST 結果未知

保留不確定狀態

無法證明未送出時，不自動重送、不換 ID 建立副本。缺少紀錄本身不是未派發的證據。

已證明本機前置失敗

受限制的重試入口

只有持久紀錄證明 sent=false，且修訂、內容、帳本與真實背景請求條件符合時，才允許沿原識別重試。

使用者取消

停止後續派發

遠端不保證立即停止。仍追蹤真正的 future；晚到回覆不能變成成功，也不能在收尾前刪除來源。

LangGraph checkpoint 只記錄控制位置，不保證 exactly-once。重新開啟 App 恢復畫面與記錄，不自動派發。遠端 thread 失效時，保留原文並由使用者預覽確認接續內容。

長期記憶是可管理的筆記

由使用者選取、預覽並確認保存，預設同助理隔離。新對話固定記憶快照，修改影響後續新對話；Skill 只使用明確選入內容。這裡沒有向量庫或背景自動學習。

備份與刪除有範圍

schema 升級先 SQLite backup，再交易遷移。多個資料庫不保證斷電原子性，還原前關閉 App 並使用一致備份。刪除本機資料不會撤回遠端歷史、獨立副本或備份。

AD 是選用接線。identity_mode=company 先通過原生登入與 authenticate hook，才建立 Store 和排程器；未接線就拒絕登入。本機 subject 目錄隔離不等同 Windows ACL 或完整多租戶授權。
06

設定三個參數，分開確認能力

endpoint、Assistant ID、API key 決定連到哪一位助理。是否能穩定聊天、產生工作格式或搜尋，仍需各自驗證。

設定

保存連線與金鑰

CA 預設系統信任，TLS 保持驗證。變更端點、ID 或相關設定會提升修訂，撤銷不再適用的能力與核准。

搜尋選用

先固定核准工具

讀取宣告後由人核對 function 名稱、schema 與範圍。metadata 成功不代表工具已實測；讀取失敗也不直接代表聊天不可用。

實測

再取得同修訂證據

明確啟動基本檢查最多 8 次合成模型請求。聊天與辨識 2 次、工作格式 3 次、自主決策 3 次，結果分開保存。

聊天通過就可以聊天，工作能力未通過不需要假裝全部啟用。搜尋另行明確測試，最多 4 次模型請求。收到文字不能代替核對工具收據或來源品質。
為什麼達哥不能只換一個 model 名稱？

已知成功契約是 Assistants 的 Threads、Messages、Runs。Assistant ID 在建立 run 時指定，不是 Chat Completions 的 model。遠端 thread 由 App 沿既有對話保留，不在退出時自動刪除。

出現 requires_action 時，只能執行既有核准搜尋。每批先完整驗證，最多 4 個工具 call、3 批與 600 秒，結果提交回原 run。模型不能指定新的 URL、headers 或本機命令。

主對話 auto 辨識、工作規劃與一般文字角色仍停用工具。正式服務失敗明確報錯，不偷偷換成示範或 Groq 回覆。

既有 API 接線說明AssistantsGateway 原始碼
診斷如何幫助下一位開發 agent？

設定頁按助理和修訂呈現聊天、需求辨識、工作格式、自主決策與搜尋結果。每項保留階段、白名單代碼、時間及錯誤編號，網路錯誤不直接斷言為 CA 問題。

最近兩個助理修訂的摘要以原子寫入保存，最多 128 位助理與 128 筆匿名對話錯誤關聯。重開時尚未結束的檢查顯示未完成，不補造成功。

查看、複製或匯出 Markdown 和安全 ZIP 不呼叫模型，也不自動上傳。摘要只供說明，不能授予能力。重測須指定目前修訂並明確同意，未知送出及未結束請求仍阻擋重送。
