# 給 GPT 6 sol：把已接通的公司助理做成可用工作流程

以下可整份貼給公司內的 GPT 6 sol 開發 agent。請在**公司目前已接通助理的專案副本**執行，不要以外部 GitHub 的示範狀態覆蓋公司修改。

---

你是這個專案的實作 agent。請直接檢查、實作及驗證，不只交付建議。遇到缺少內部契約、權限或產品選擇才問我；其他可独立完成的工作繼續進行。

## 已知現況與這次目標

我已能在公司連上助理，但完整產品流程還沒完成。這是使用者回報的公司現況；請以公司 checkout 的程式及實測為準，不要假設每個 assistant ID 都已驗證。

我要的核心價值是：

**說出需求 → 主代理追問必要條件 → 顯示簡短分工 → 我確認一次 → 子代理依序完成 → 原對話查看成果 → 成功後可另行授權定時執行。**

主介面維持 WebView，保留 Tkinter 備用。一般聊天直接回覆；需要執行工作的 Plan 必須先確認。不要把主要成果停在改信件、文字摘要或增加畫面裝飾。

## 先做現況盤點，保留公司已接通的成果

1. 讀取 `AGENTS.md`、`README.md`、`docs/PROJECT.md`、`docs/VALIDATION.md`、`COMPANY-HANDOFF.md`。檢查 Git 狀態、公司新增 adapter、目前成功呼叫入口及既有測試；不要重設分支、覆蓋未提交變更或直接搬回外部示範 adapter。
2. 以短表列出「已可用／只有 UI 或 mock／尚缺」，至少涵蓋一般對話、planner、各子代理、session 隔離、批准、成果、排程。程式裡有函式或畫面，不等於公司功能已完成。
3. 沿用目前成功 API 的 endpoint、認證、assistant ID 傳送位置、request/response 及 session 規則。不猜 assistant ID 等於 model，不重新發明一套請求格式。
4. 列出已配置助理的名稱、角色及能力狀態。先確認自動流程使用的是唯讀文字／RAG 助理；未知的寄信、寫入或其他原生工具能力不得在規劃期間被觸發。
5. 缺資訊時集中詢問：成功範例／設定存放位置、有哪些可用角色、第一個試跑需求及核准資料來源。不要要求我將 API key、密碼或真實公司資料貼入 Git 文件。

## 第一階段：先交付一條完整、真實的最小工作流程

優先用我輸入的一段**核准可送公司助理的文字**當來源，不以 Oracle、AD 改造或 LangGraph 整合當作這條流程的前置條件。未完成正式授權時限目前本人測試，不因此開放全單位。

在主對話完成下面旅程：

1. 切換到清楚標示的公司模式，顯示目前助理。示範模式仍保留；公司呼叫失敗必須報錯，不能用示範答案補位。
2. 使用者選「規劃工作」並輸入需求。planner 可以討論與追問，但不能查資料、派發子代理、儲存啟用排程。缺必要條件時最多三題；未知資料就明示。
3. 條件完整後呈現最多六個依序步驟，顯示每步用途、助理名稱、輸入來源及資料去向。支援修改與取消，不要求一般使用者編輯 JSON。
4. 按一次 **「確認執行」** 才授權當下可見的修訂，服務層檢查綁定、期限及 request ID。修改後舊確認失效；連點、重開或晚到回覆不會重複派發。
5. 依序執行 **分析 → 覆核 → 彙整**，每位助理只收到已批准的必要內容。覆核 `needs_attention` 時停止後續，顯示原因與已取得成果，不能為了完成流程而放行。
6. 原對話可看真實狀態、取消及成果卡。先呈現結論、需要注意、待確認事項，再展開分工。AI 文字不是已驗證事實；保留來源和限制，沒有資料不能補造。

如果公司暫時只有一個可用 ID，可先驗一般對話或明確標示的單助理流程；不得把同一助理重複呼叫宣稱為公司多 ID 驗收。缺少角色時保留清楚的待配置狀態。

**本階段完成條件：**不用切進階頁，在主畫面以真實公司助理完成一次上述旅程；確認前沒有業務步驟派發，完成後可核對來源、角色及成果。另測缺条件、回覆格式錯誤、逾時、取消與重複確認。

## 第二階段：把新版任務草稿接到既有執行機制

- 保留「一般聊天／建立任務」與目前無附件的主畫面。切模式／助理開始新的對話，不混用歷史或把舊 Plan 改送另一個目標。
- `dialogue-v1.sqlite3` 的 `task_drafts.enabled CHECK=0` 是刻意的界線。**不要直接改成 1、移除 CHECK，或讓 scheduler 讀它。**
- 增加明確的「轉為執行計畫」流程：把已驗證草稿映射到既有 WorkflowService 的草稿／預覽；再次呈現實際分工與資料去向，由使用者確認執行。保存任務草稿本身仍不執行。
- 以來源 ID、修訂及固定 request ID 記錄轉換關係，重複點擊不得建立多份工作。不能沿用過期預覽或把「確認儲存」視為「確認執行」。
- 任務類型、來源、助理與步驟均使用可信目錄及服務層驗證；模型不能創造工具、shell、檔案讀取或任意 SQL。
- 一般聊天不增加工作批准；工作流程只保留必要的一次執行確認，不額外要求逐步批准。涉及新的資料來源或超出已批准範圍時停下來重新確認。

**完成條件：**建立任務 → 修改預覽 → 保存未啟用草稿 → 轉成計畫 → 確認執行 → 成果，能在同一介面完成。取消保存或取消執行皆不產生未授權工作。

## 第三階段：成功流程才可以安排自動執行

- 沿用現有排程服務，固定使用成功驗證的流程版本和助理綁定，不另寫第二個 scheduler。
- 使用者另行核對台北時間、頻率、來源及持續傳送範圍，明確按「確認啟用」。單次執行批准不等於每天傳資料的授權。
- 第一條排程可以重用已批准的固定文字，但要顯示「固定輸入，不會取得新資料」。需要每天查最新資料時，必須先接核准查詢／資料服務；不能用舊文字或示範資料假装日報已更新。
- 提供「現在測試一次／暫停／查看最近結果／下次時間」。立即測試不改变原定時間，App 關閉後不執行；不新增 Windows 常駐服務。
- 每次派發檢查公司身份／憑證／能力及助理版本；失效或未完成授權就停止，不能借 UI 隱藏當權限檢查。重啟、漏跑、防重、取消、失敗後暫停沿用既有契約。
- 真 Oracle 尚未接通時，資料查詢入口顯示未配置；不要假裝已能查公司 DB，也不要為此阻止前兩階段的核准文字流程完成。

**完成條件：**本人測試範圍內，成功流程能明確啟用、立即測試、查看結果並暫停；沒有重複觸發，資料來源及新鮮度如實顯示。單位部署及 AD／Oracle 驗收另依公司工作單完成。

## 驗證、資料界線與交付

- 保護既有公司變更及資料；有 schema 變更先用 SQLite backup 備份，再交易遷移與失敗回復測試。不得直接降低資料版本。
- 使用現有金鑰安全儲存，UI 顯示公司／示範的真實狀態；不把金鑰、內部網址實值、公司內容、HTTP body、checkpoint 或本機 DB 提交 Git。不得送公司資料到 Groq 或 LangSmith；不得關 TLS／防毒。
- 模型回覆視為不可信：驗證 JSON、步驟、助理、參數及來源；`facts` 沿用既有契約，不靠 prompt 代替程式驗證。普通模型文字不能直接觸發儲存、執行或讀檔。
- UI 保留草稿、選取和捲動；取消後晚到結果不變成功，不復活已刪對話。執行中的真實 future 沒結束前不釋放相關保護。
